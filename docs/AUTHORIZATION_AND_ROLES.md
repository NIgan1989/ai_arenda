# Авторизация, роли и полномочия ассистента

Обновлено 22.10.2026. Теперь перед рабочими страницами обязательны вход и выбор роли; [реализация страниц и проверок](ROLE_PAGES.md). Этот документ отделяет действующий локальный пилот от целевой архитектуры. Права на действия проверяет сервер. Выбранный в интерфейсе сценарий или текст модели не являются разрешением.

## Что уже работает

| Часть | Веб | Мобильный пилот |
| --- | --- | --- |
| Вход | Платформенная авторизация ChatGPT; в portable dev — учебная идентичность | Логин и пароль; хеш scrypt с солью; случайная сессия на 7 дней |
| Проверка запроса | ID из доверенных заголовков платформы | Bearer-токен, в базе хранится только его SHA-256 хеш; проверяется срок |
| Выход | Платформенный выход | Отзыв текущей сессии на сервере |
| Хранение сессии клиента | Платформенная сессия | SecureStore на телефоне, память вкладки в веб-просмотре |
| Общая учётная запись между клиентами | Пока отсутствует: отдельные идентичности и базы | Пока отсутствует |
| Проверка телефона, личности, права сдавать объект | Пока отсутствует | Пока отсутствует |

Веб-приложение доверяет заголовкам `oai-authenticated-*` только за платформенным шлюзом, который обязан удалять присланные клиентом значения и выставлять собственные. Самостоятельное размещение этого обработчика в интернете требует полноценной проверки сессии либо доверенного шлюза. Учебный вход portable dev не предназначен для внешнего доступа.

Роли `guest`, `owner`, `cleaner` сейчас заявлены пользователем в профиле. Их можно совмещать. Это не подтверждение собственности, квалификации или личности. В пилоте роль владельца позволяет создать собственное объявление, поэтому публикацию реальных объявлений нужно закрыть проверкой до публичного запуска.

## Действующие ограничения по объектам

- Гость читает свои брони, отправляет заявки, отменяет незавершённую бронь до фактического заселения и сообщает о выезде. Счётчик ролей в интерфейсе не даёт доступа к чужим броням.
- Владелец меняет тарифы, готовность, брони и задания только своих квартир: проверяются `properties.owner_id` / `cleaning_jobs.owner_id`. Подтверждение оплаты и депозита доступно владельцу; это ручная отметка фактического поступления, не банковская операция.
- Исполнитель видит открытые задания без адреса и контакта. После назначения получает адрес и контакт заказчика, может начать работу и отправить отчёт только по своему назначению. Приёмка доступна владельцу.
- Адрес доступен гостю после подтверждения брони. Личные диалоги и уведомления выбираются по ID авторизованного пользователя. Хранилище документов клиента ещё не реализовано.
- Начало уборки связанной брони запрещено SQL-триггером до подтверждения освобождения квартиры владельцем. Сообщение гостя «я выехал» не делает квартиру готовой. После отчёта требуется приёмка; блокировку на ремонт приёмка не снимает.

Тесты отдельно проверяют, что пользователь, заявивший все три роли, не получает доступ к квартире и брони другого владельца.

## Где сейчас ассистент

Текущий интерфейс — сценарный помощник: собирает сведения и вызывает ограниченные серверные операции после предусмотренного подтверждения. Необязательный языковой адаптер генерирует текст, но не имеет инструментов изменения бронирований, денег, ролей или доступа. Сценарий разговора `actor=owner` помогает показать нужные вопросы, но сервер не доверяет этому значению для выдачи прав.

Автоподтверждение брони включается владельцем отдельно для конкретной квартиры. Правило хранит версию, тарифы, депозит, условия, стоимость уборки и лимит. Система ещё раз проверяет разрешение и версию перед подтверждением. Событие записывается с исполнителем `system:rental-policy`, владельцем, от чьего имени оно выполнено, квартирой и версией правил. Действие не выдаётся за ручное решение владельца и не подтверждает получение денег. Это ограниченный автоматический процесс, пока не автономный языковой агент.

## Как должен работать единый сервис

Один постоянный `user_id`, единый сервер авторизации и одна база для сайта и приложения. Вход по проверенному телефону; при необходимости дополнительное подтверждение опасного действия. Контакт из анкеты не заменяет проверенный телефон. Предусмотреть выход со всех устройств, отзыв сессий и восстановление доступа.

Роли и доверие хранятся отдельно:

- `user_roles`: заявленный вид деятельности и состояние проверки `pending / verified / suspended`.
- `property_memberships`: право конкретного пользователя управлять конкретной квартирой, набор разрешений, кто выдал доступ, срок и отзыв. Владелец может уполномочить управляющего без передачи аккаунта.
- Бронь связывает гостя с квартирой; назначение связывает исполнителя с заданием. Пользователь с ролью уборщицы не получает доступ ко всем адресам.
- Администратор платформы — отдельный сотрудник с ограниченными административными разрешениями, усиленным входом и журналом. Пользователь не может назначить себе эту роль через профиль.

Ассистент работает как отдельный сервисный субъект. Для каждого вызова инструмента сервер определяет инициатора, объект, цель, актуальное разрешение, лимиты и допустимый переход статуса. Самостоятельно выдавать себе роли, расширять полномочия, менять платёжные реквизиты или читать документы всех клиентов он не может. Отзыв поручения или блокировка участника немедленно запрещают новые действия, включая запланированные.

Разговоры каждого участника приватны и связаны общей бронью. Например: гость сообщает о выезде → система уведомляет владельца → освобождение подтверждается уполномоченным способом → исполнитель получает задание и разрешённые сведения → отчёт поступает на приёмку → готовность обновляется после проверки. Полные переписки, документы гостя и внутренние финансовые лимиты владельца между сторонами не пересылаются.

Полномочия владельца задаются один раз и уточняются при изменениях: какие брони подтверждать, допустимая стоимость и скидка, депозит, лимит уборки, исполнители, сроки и ситуации для передачи человеку. Поэтому ассистент не должен запрашивать разрешение на каждый обычный шаг. Спор, удержание депозита, выход за лимит или неподтверждённое состояние требуют отдельного решения.

Память о клиенте хранится в разрешённых структурированных записях, а не в общем контексте модели. Повторная проверка зависит от срока действия и отзыва подтверждения. Проверку и хранение документов, сроки удаления и доступ нужно внедрять отдельным защищённым процессом; сейчас эти возможности отсутствуют.

## Следующий порядок реализации

1. Единый API и учётные записи для веба и телефона; перенос пилотных идентичностей без объединения людей только по похожему имени или контакту.
2. Проверенные контакты и роли, приглашения управляющим, проверка допуска объявления к публикации.
3. Разрешения по объектам, поручения сервисному субъекту, журнал фактически выполненных и отклонённых команд.
4. Подключение инструментов модели к тем же операциям и ограничениям; отдельные контексты участников, повторная проверка полномочий при выполнении отложенной команды.
5. Реальные подтверждения платежей, проверка личности, защищённые документы и доставка сообщений через выбранных поставщиков.
