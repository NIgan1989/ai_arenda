# AI администратор: локальная операционная версия

Обновлено 28 октября 2026. Экран `/workspace/<роль>/operations` («Управление») доступен владельцу, гостю и исполнителю. Данные и действия ограничены аккаунтом и текущей ролью. Внешние подключения пока отсутствуют. Сервис не отправляет реальные сообщения и не принимает банковские платежи без настройки провайдера.

## Что работает

- Постоянные задачи цепочки: заявка → подтверждение → оплата/депозит → заезд → выезд → уборка → приёмка → расчёт. Просрочки и нерешённые обращения видны ответственным участникам.
- Очередь фоновых операций с арендой задания, восстановлением прерванного выполнения, увеличением задержки и ручным повтором после восьми неудач. Один проход обрабатывает до 12 заданий. Таймер локального запуска вызывает обработчик примерно каждые 30 секунд.
- Поручения из веб-чата: создать уборку, запросить продление, передать обращение, запустить подбор. Модель подготавливает проверяемую карточку; пользователь подтверждает действие. Сервер повторно проверяет права, время, версии правил и лимиты. Срок карточки — 15 минут. Ключи операций защищают повтор запроса после сбоя.
- Предложения свободным исполнителям, которые включили их получение. В предложении сохранены время, цена и условия замены. Назначение требует согласия исполнителя и полномочий владельца. Замена неявившегося исполнителя возможна только по принятому условию, при свободной квартире, до начала работы и после 15 минут от начала задания и принятия предложения.
- Приватные JPEG-фото до/после/повреждений: загрузка назначенным исполнителем во время работы, просмотр владельцем и этим исполнителем. До 24 фото на работу; EXIF удаляется. Владелец может потребовать фото до и после для сдачи и приёмки. Локально фото находятся в базе и попадают в полную резервную копию.
- Неизменяемый журнал частичных оплат, депозитов, возвратов, выплат исполнителю, расходов и компенсаций. Депозит учитывается отдельно от результата аренды. Ручная запись фиксирует уже выполненный вне сервиса перевод. Она не отправляет деньги. Остатки и допустимые суммы проверяет сервер.
- Инструкции доступа зашифрованы AES-GCM. Каждое открытие проверяет роль, назначение/бронь, время, оплату, депозит и готовность квартиры. Факт открытия записывается. Смена физического кода замка остаётся действием владельца.
- Заявки на проверку владельца/объекта и исполнителя, решение только уполномоченного администратора платформы. Статус проверки отделён от роли. Это журнал фактической ручной проверки, а не подключённый государственный KYC.
- Ручной импорт ICS, отзыв экспортных ссылок и экспорт занятых интервалов без адресов/контактов. Есть адаптер регулярного HTTPS-обновления разрешённых источников. Ошибка импорта сохраняет прежние блокировки. Автоматический источник без успешного обновления более часа блокирует новые брони до восстановления или явного отключения владельцем.

## Запуск и миграции

Нужен Node.js 24+. В этой рабочей базе миграции `0000`–`0011` уже применены. SQL-файлы `drizzle/*.sql` — последовательный источник ограничений базы; существующие миграции не редактировать. Декларации `db/schema.ts` описывают исходную часть проекта и не заменяют полный набор SQL-миграций.

Для существующей базы с `0000`–`0007`:

```powershell
node scripts/setup-administrator.mjs
node scripts/setup-operations.mjs
node --import ./scripts/sites-env.mjs scripts/start-local.mjs
```

`setup-operations` создаёт ключ локального шифрования при отсутствии, делает зашифрованную копию и применяет недостающие `0009`–`0011`. Для совершенно новой веб-базы сначала последовательно применить `0000`–`0007`. Мобильный сервер применяет собственную совместимую последовательность при запуске; его авторизация отдельная, сообщения модели остаются сценарными. Общие операции и права совпадают.

Пока компьютер, сервер или процесс администратора выключены, фоновых проверок нет. Код обработчика `scheduled` подготовлен, но круглосуточное размещение и расписание в облаке не настроены.

## Резервные копии и восстановление

Локальный процесс после успешного прохода сохраняет полную согласованную SQLite-копию раз в сутки, оставляет 14 последних автоматических копий в `outputs/backups/`. Перед миграцией создаётся дополнительная копия. Копии защищены AES-256-GCM ключом `ACCESS_ENCRYPTION_KEY` из `.dev.vars`. Этот ключ нужен и для инструкций доступа: сохраните его отдельно в защищённом месте. Потеря ключа делает расшифровку невозможной. Хранение на том же диске не защищает от потери всего компьютера; перенос в отдельное хранилище — следующий этап подключения.

Принудительно создать копию:

```powershell
node scripts/local-backup.mjs create
```

Проверить восстановление в **новый**, ещё не существующий файл внутри проекта:

```powershell
node scripts/local-backup.mjs restore --file outputs/backups/<имя>.sqlite.enc --target outputs/recovered.sqlite
```

Восстановление проверяет целостность и не перезаписывает рабочую базу. Переключение сервера на восстановленную базу требует остановки сервера и отдельной проверки выбранного файла. Отдельный адаптер снимков в объектное хранилище доступен при `BUCKET`, но ограничен пилотным объёмом: до 5000 строк на таблицу и 4 МиБ JSON. Он не заменяет полную SQLite-копию; при хранении фото в R2 нужны отдельные копии объектов. Сейчас R2 не подключён.

## Контракты будущих подключений

Пример имён настроек: [configuration.example](configuration.example). Значения задаются только на сервере; `.dev.vars` исключён из Git. В интерфейсе сохраняются пользовательские согласия и статусы, а не ключи провайдеров.

**Telegram:** токен/имя бота и секрет webhook. `POST /api/hooks/telegram` проверяет `X-Telegram-Bot-Api-Secret-Token`. Одноразовая ссылка `/start` привязывает только личный чат к текущему аккаунту/роли. Доставка включается пользователем. Telegram не даёт здесь достоверных отметок прочтения; успешный API-ответ означает принятие сообщения.

**SMS/WhatsApp:** HTTPS-шлюз с Bearer-токеном. `POST` получает `{id,to,text,category}`, заголовок `Idempotency-Key`, отвечает JSON `{id}` после фактического принятия. Для SMS-кода `category=verification`, уведомления — `notification`. Канал включается только на подтверждённый номер веб-аккаунта. OTP живёт 10 минут, повтор через 60 секунд, максимум пять попыток; в базе хранится хеш. Внешние уведомления содержат общий текст и ссылку, без адресов, кодов и содержания обращений.

Подтверждения SMS/WhatsApp: `POST /api/hooks/delivery`, тело `{channel,eventId,outboxId,status}`, где `channel=sms|whatsapp`, `status=delivered|read|failed`. Шлюз должен нормализовать фактические события своего провайдера. Не создавать событие `read` без такого подтверждения.

**Платёжный шлюз:** `POST` по `PAYMENT_GATEWAY_URL` с Bearer-токеном и `Idempotency-Key`; точный контракт тела/ответа находится в `createPaymentIntent` (`lib/finance.ts`). Подписанное событие оплаты принимает `/api/hooks/payment`; событие обязано соответствовать ранее созданному намерению, провайдеру, сумме и KZT. Прямых банковских адаптеров Kaspi Pay/Halyk и автоматических возвратов пока нет. Их реализация требует выбранного банковского продукта, договора и документированного API после оформления бизнеса.

Запрос шлюзу: `{intentId,amount,currency:"KZT",kind,returnUrl}`, где `kind=payment|deposit`, сумма — целые тенге. Ответ: `{intentId,reference,checkoutUrl}` с тем же ID и HTTPS-ссылкой. Успешное подписанное событие: `{eventId,intentId,type:"payment.succeeded",currency:"KZT",amount}`. Это внутренний контракт адаптера, а не формат API какого-либо банка.

Оба общих webhook используют `X-Event-Timestamp` (Unix-секунды), `X-Event-Signature` (hex HMAC-SHA256 от `timestamp + '.' + исходное тело`). Секрет не короче 32 символов, допустимый сдвиг времени пять минут. Повторы одинакового события безопасны; изменение тела с тем же ID отклоняется. Обработчики не доверяют заявленной в JSON личности пользователя.

**Календари:** принимаются разовые интервалы VEVENT с UTC, датами или `Asia/Almaty`/`Asia/Qostanay`. Повторения, неизвестные часовые пояса и время без зоны отклоняются полностью, чтобы не принять неполную занятость за свободное время. Лимит 512 КБ/1000 событий. Ссылки источников секретны; клиент получает метаданные. Экспортная ссылка действует 90 дней и может быть отозвана. ICS не даёт мгновенной блокировки на сторонней площадке: конфликт, уже возникший между обновлениями, требует решения владельца.

## Проверки

```powershell
node node_modules/typescript/bin/tsc --noEmit
node --test tests/*.test.mjs
node scripts/test-api.mjs
node scripts/run-framework.mjs build
```

Проверяются роли, параллельные возвраты, повторные запросы, восстановление поручений, аренда очереди, проход по 200 заданиям, приватность фото/доступа, подписи событий, неподключённые провайдеры, HTTP-лимиты и восстановление зашифрованной копии. Контракты внешних провайдеров проверяются тестовыми ответами. Это не проверка боевого банковского или мессенджерного аккаунта и не доказательство промышленной нагрузки.
