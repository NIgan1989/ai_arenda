# Допуск к работе и очередь оператора

Локальная миграция `0013_pilot_governance.sql` добавляет настраиваемую политику допуска, очередь на основе существующих обращений и историю их разбора. Новых внешних проверочных сервисов она не подключает.

## Правила допуска

Политика хранится в единственной записи `pilot_policy`. Исходно обязательные проверки отключены, чтобы сохранить работу текущего локального пилота. Серверный администратор платформы может включить:

- проверку владельца **и конкретного объекта** до публикации и новых броней;
- проверку исполнителя до нового назначения;
- подтверждение номера аккаунта для владельца/гостя при бронировании, для владельца при публикации и для исполнителя при назначении.

Изменение требует явного подтверждения, актуальной версии и серверного признака `platformAdmin`. Выбор роли владельца не даёт административных прав. Результаты проверок берутся из `participant_reviews`: последняя запись по нужной роли и объекту должна быть одобрена, а срок её действия — не истечь. Более поздняя отклонённая или ожидающая запись не позволяет использовать старое одобрение.

Подтверждённый телефон проверяется по `phone_verifications` и текущему номеру входа в `auth_accounts`, а не по редактируемому контакту профиля. Нативный логин без телефонной идентичности не удовлетворяет обязательному телефонному допуску. Перед его включением нужно подключить рабочий SMS-канал и предусмотреть проход участников через проверку.

При обязательной проверке владельца новую квартиру сначала сохраняют черновиком. После положительного решения можно публиковать её. Каталог должен использовать `pilotPropertyVisibleSql()`; он скрывает недопущенные объекты при включённой политике. Флаг публикации и история карточки не уничтожаются.

SQL-триггеры защищают финальную запись публикации, активной брони и нового назначения от смены политики между проверкой и записью. Исключение — изолированные учебные объекты. Уже начатую работу, факт проживания, записи оплат и принятый результат изменение политики не отменяет. Окончательное освобождение квартиры и переводы по-прежнему фиксируются отдельными доменными действиями.

## Обращения и оператор

Для каждой записи `administrator_issues` существует не более одной карточки `operator_tickets`; связь хранится в первичном ключе `issue_id`. Обращение из брони/задания автоматически появляется в соответствующей очереди. Владелец видит обращения по своим объектам, гость — по своей брони, исполнитель — по назначенной ему работе. Только серверный администратор платформы получает общую очередь.

Оператор может взять обращение на себя, вернуть в общую очередь, назначить приоритет и срок ответа, написать публичный комментарий или внутреннюю заметку, закрыть разбор с основанием и открыть повторное рассмотрение. Назначить самого себя оператором через тело пользовательского запроса нельзя: маршруты обязаны передавать `platformAdmin`, вычисленный из серверной конфигурации.

Закрытие и повторное рассмотрение требуют предварительно взять обращение в работу. Закрытие дополнительно требует явного подтверждения. Решение всегда видно сторонам; внутренние заметки доступны только операторам. Участники могут добавлять комментарии, но не менять оператора, приоритет или статус.

Каждая мутация проверяет версии исходного обращения и карточки оператора, сохраняет историю и аудит в одной транзакции. `requestKey` защищает повтор после сетевого сбоя; тот же ключ с другим содержанием отклоняется. Закрытие одновременно меняет исходное обращение, поэтому AI администратор перестаёт считать его открытым. Если обращение закрыто через существующую карточку участника, очередь синхронизирует этот результат.

Операторская запись **не является** банковским возвратом, подтверждением выезда или приёмкой уборки. Эти факты не меняются при разборе обращения.

## Подключение к интерфейсу и маршрутам

- `governanceState(service, role, platformAdmin)` → `state.governance`;
- `savePilotPolicy(service, body, platformAdmin)` → `governance/policy`;
- `updateOperatorTicket(service, role, body, platformAdmin)` → `governance/ticket`;
- `<PilotGovernance state={state.governance} role={role} mode="admissions" save={send} busy={busy}/>`;
- тот же компонент с `mode="operator"` показывает общую очередь администратору и личные обращения участникам.

Все маршруты сначала проверяют авторизацию текущей рабочей роли. Прямые вызовы экспортированных функций из доверенного серверного кода также требуют проверенного административного признака.

Проверки: `node --test tests/pilot-governance.test.mjs`. Тесты проверяют обязательное согласие, права, устаревшие версии, истёкшие/отозванные проверки, телефонную идентичность, SQL-защиту, приватность внутренних заметок, повтор запроса и сохранение фактов денег/готовности при закрытии спора.
