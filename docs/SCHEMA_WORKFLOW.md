# Схема, миграции и автоматические проверки

Единственный источник устройства базы — последовательные SQL-миграции `drizzle/0000_*.sql`, `0001_*.sql` и далее. Они включают таблицы, индексы, ограничения, триггеры **и преобразования данных**. Уже зафиксированные миграции не редактируются и не переименовываются: изменение оформляется следующим номером.

`db/current-schema.sql` — автоматически построенный полный снимок DDL из SQLite после всех миграций. В заголовке записаны имена и SHA-256 нормализованных миграций. Это справочник и проверяемый результат, а не скрипт установки: миграции содержат также начальные данные и перенос истории, которых в DDL-снимке нет.

`db/schema.ts` содержит прежние частичные ORM-декларации для совместимости исходников. Он явно помечен справочным. Генерация и `push` через `drizzle-kit` остановлены в `drizzle.config.ts`, чтобы устаревший ORM-снимок не породил удаление рабочих таблиц и триггеров. Нельзя включать их, просто убрав защиту: сначала требуется отдельная полноценная стратегия переноса ручной истории и ограничений.

После добавления **новой** миграции:

```powershell
node scripts/schema-snapshot.mjs --write
node scripts/verify-local.mjs
```

Без изменения файлов, для проверки:

```powershell
node scripts/schema-snapshot.mjs --check
```

Проверка создаёт только базы в памяти. Она не читает `.dev.vars`, не подключается к рабочей SQLite/D1 и не применяет миграции к пользовательским данным. Последовательно проверяются:

1. Непрерывная уникальная нумерация с `0000`, наличие и неизменность всех ранее записанных SHA-256. LF/CRLF нормализуются, поэтому обычная настройка Git в Windows не даёт ложных изменений истории.
2. Установка с нуля с `foreign_keys=ON`, транзакцией для каждого файла и SQLite-проверками целостности.
3. Обновление каждого префикса истории остальными миграциями; конечная схема должна совпасть с чистой установкой.
4. Полное совпадение актуального результата с сохранённым `db/current-schema.sql`.

`--write` также запрещает переписать ранее известную миграцию. При ошибке восстановите прежний файл и добавьте новую миграцию. Не редактируйте хеши снимка вручную. Сценарии переноса реальных записей дополнительно покрывают бизнес-тесты; проверка пустых схем не заменяет резервное копирование и испытание копии производственной базы.

`node scripts/verify-local.mjs` запускает последовательно: проверку схемы → TypeScript → все основные тесты → HTTP-тесты мобильного/общего сервера → production-сборку. Нужен Node.js 24+. Публикации, внешних платежей, сообщений и API-вызовов OpenAI этот сценарий не делает; тесты используют вымышленные данные и подменённые ответы.

`.github/workflows/check.yml` запускает тот же набор на push/pull request с Node 24 и установкой по lock-файлу. Workflow имеет только чтение репозитория, не получает секреты приложения и не публикует сервис. Файл начнёт исполняться после размещения репозитория в GitHub; добавление его локально не означает, что удалённая CI-проверка уже запускалась.

Применение к рабочей базе выполняется отдельно действующим setup-скриптом после зашифрованной копии. Автоматическая проверка не запускает setup и не изменяет установленную схему.
