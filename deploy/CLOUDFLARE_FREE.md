# Бесплатный пилот в Cloudflare

Проверено 11 ноября 2026. Подходящее назначение для текущего Worker/D1-приложения — Cloudflare Workers Free и D1. Приложение опубликовано: https://ai-arenda.ai-arenda-kz.workers.dev. Авторизация Cloudflare выполнена через Wrangler; серверные секреты переданы после отдельного согласия пользователя. Сохранённый проект Sites недоступен в текущем подключении; его идентификатор не заменяли.

Бесплатный тариф имеет ограничения: 100 000 запросов Workers в день и 10 мс CPU на вызов; D1 — 5 млн прочитанных строк и 100 000 записанных строк в день, 5 ГБ общего хранилища. Превышение бесплатных квот может останавливать операции. Производительность авторизации с PBKDF2 и фоновых проходов нужно измерить в облаке: локальные проверки не доказывают соблюдение лимита CPU. Хеширование паролей ради бесплатного тарифа не ослаблять. Не включать Workers Paid и платные дополнительные продукты без отдельного решения пользователя.

Источники: [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/), [workers.dev](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/). Адрес `workers.dev` позволяет начать без покупки домена. Расходы внешних API не входят в тариф хостинга.

## Подготовлено в проекте

- В итоговую конфигурацию сборки включено расписание `* * * * *` для уже существующего фонового обработчика.
- `scripts/prepare-cloudflare.mjs` создаёт отдельную конфигурацию в игнорируемой `.sites-runtime/cloudflare/`, требует реальные ID аккаунта и D1 и отклоняет заглушки. Исходный manifest Sites сохраняется.
- Локальные ключи, внутренние сервисы предпросмотра и сеансы не копируются в конфигурацию размещения.
- Миграции схемы находятся в `drizzle/`. Runtime-секреты должны передаваться в защищённые bindings, а не в публичные файлы или переменные клиентской сборки.

## Порядок подготовки и повторного размещения

1. Войти в бесплатный аккаунт: `node scripts/cloudflare-local.mjs login`. Пароль и подтверждения аккаунта вводит пользователь. Эта оболочка сохраняет OAuth-состояние только в игнорируемой `.sites-runtime/cloudflare-auth/`; следующие команды Wrangler также выполнять через неё.
2. Создать отдельную D1-базу `ai-arenda` и получить ID аккаунта/базы. Выполнить сборку.
3. Создать конфигурацию: `node scripts/prepare-cloudflare.mjs --database-id <UUID> --account-id <ID>`.
4. Применить миграции к новой облачной базе. Перенести только сохранённую учётную запись администратора, её хеш пароля и резервного кода и минимальный профиль. Не переносить локальные cookie-сеансы или старую резервную копию с объявлениями. До импорта убедиться, что облачная база новая/пустая.
5. Настроить секреты через Wrangler stdin: `ACCESS_ENCRYPTION_KEY`, `ADMINISTRATOR_RUNNER_SECRET`, `PLATFORM_ADMIN_IDS`, необязательный email-псевдоним и параметры OpenAI. Для `SITE_PUBLIC_URL` использовать настоящий HTTPS-адрес. Не печатать значения и не включать их в Git.
6. Опубликовать Worker с `.sites-runtime/cloudflare/wrangler.json`. Проверить вход администратора, пустой каталог, регистрацию обычного аккаунта, права и работу расписания. Проверить лимит CPU на входе/регистрации и фоновых проходах.
7. Проверить внешнее восстановление и уведомления. Проверка полного зашифрованного экспорта/импорта в отдельную облачную D1 выполнена 11 ноября 2026; рабочая база не восстанавливалась. Регулярные внешние копии и физические устройства требуют отдельного контроля.

## Автоматическая публикация из GitHub

С 12 ноября 2026 в репозитории есть `.github/workflows/deploy.yml`. После каждого слияния в main, когда проверки `Check local application` на этом коммите прошли, GitHub сам собирает проект, применяет новые миграции D1 и публикует Worker, затем проверяет, что главная, вход и каталог отвечают 200. Запустить вручную можно на странице Actions кнопкой Run workflow.

Нужен один секрет репозитория (Settings → Secrets and variables → Actions): `CLOUDFLARE_API_TOKEN` — токен Cloudflare с правами Account → Workers Scripts: Edit, Account → D1: Edit, Account → Workers R2 Storage: Edit и Account → Account Settings: Read, ограниченный этим аккаунтом. Аккаунт и базу D1 `ai-arenda` публикация находит сама этим токеном (`scripts/resolve-cloudflare-ids.mjs`) и скрывает их в журнале. Если токен видит несколько аккаунтов, добавьте секрет `CLOUDFLARE_ACCOUNT_ID`; `CLOUDFLARE_D1_DATABASE_ID` тоже можно задать явно.

Пока секрета нет, публикация пропускается с пометкой, а не падает. Серверные секреты приложения (OpenAI, ключи шифрования, VAPID) в GitHub не передаются: публикация идёт с `--keep-vars` и оставляет те, что уже сохранены в Cloudflare. Менять их по-прежнему нужно локально через `node scripts/deploy-cloudflare.mjs`. Адрес сайта для проверки можно переопределить переменной репозитория `ARENDA_PUBLIC_URL`.

## Очистка локального приложения

По явному запросу пользователя выполнена очистка объявлений, пользователей и операций, кроме администратора. Пароль, резервный код и действующие сеансы администратора сохранены. Перед очисткой создана зашифрованная копия и проверено её восстановление. Отчёт без секретов: `outputs/maintenance/admin-only-reset.json`. Старые данные остаются только в защищённой резервной копии для отката; автоматически возвращать её в рабочий сервис нельзя.

`node scripts/reset-local-data.mjs --keep-admin-only` — разрушительная команда обслуживания, которая требует отдельного явного запроса на очистку. Не добавлять её в запуск, CI, подготовку хостинга или миграции.

## Фактическая проверка размещения

11 ноября 2026: создана отдельная база D1 ai-arenda, при первом размещении применены 30 миграций. В облаке один аккаунт и один профиль администратора, ноль объявлений и броней. Хеши пароля/восстановления сохранены; сеансы из локального окружения не переносились. Для новых владельцев и исполнителей включена ручная проверка допуска; обязательная проверка телефона не включена без SMS-провайдера.

Проверены HTTPS главной и входа (200), пустой каталог (200), перенаправление анонимного /admin на вход и отказ управляющего API без сеанса (401), успешный вход администратора по email и доступ к обзору. Тестовый облачный сеанс завершён. Первый ручной проход фоновых задач завершил 2 задачи без ошибок; расписание раз в минуту прикреплено к Worker. Доступность Time Travel подтверждена получением bookmark, но реальное облачное восстановление ещё не испытывалось.

Healthcheck честно показывает needs_attention до подтверждения внешних копий и автоматических фоновых проходов. Не подменять эти проверки фиктивной отметкой резервного копирования. Уведомления вне приложения и физические устройства остаются отдельными этапами.

Обновление итоговой проверки: клиентские JS-файлы отдаются напрямую через Workers Assets (200); вход администратора через облачный интерфейс проверен. Автоматическое расписание подтверждено свежим heartbeat после ручного старта (34 секунды при повторной проверке спустя несколько минут). Итоговый healthcheck остаётся needs_attention из-за непроверенного внешнего резервного восстановления. Сеанс администратора во внутреннем браузере оставлен для пользователя.

## Push и проверка восстановления, 11 ноября 2026

Добавлена миграция 0030, браузерная очередь push, настройки в профиле и подключениях, Service Worker и manifest. Ключи VAPID хранятся только в серверных secrets; инструкция в [WEB_PUSH.md](../docs/WEB_PUSH.md). Приём запроса провайдером не подтверждает отображение на устройстве. Физическая доставка должна быть проверена пользователем после выдачи разрешения.

Полная облачная копия (включая аватар администратора и хеши входа) зашифрована AES-GCM, прочитана обратно и импортирована в отдельную временную D1. Сверены количества и содержимое всех таблиц, foreign_key_check и quick_check. Тестовая база удалена, открытые SQL-файлы удалены. Отчёт и зашифрованная копия остаются в игнорируемой outputs/backups. Скрипт повторения: `node scripts/verify-cloudflare-recovery.mjs .sites-runtime/cloudflare/wrangler.json`. Он не восстанавливает production.

Найдена и устранена проблема: стандартный экспорт D1 создаёт слишком длинный INSERT для изображений, хранящихся в базе. Восстановление разбивает такие строки на ограниченные команды, затем сверяет полное содержимое с исходной копией. Для больших объёмов нужна порционная проверка и отдельное файловое хранилище.

Time Travel в D1 включён автоматически; на Free история составляет 7 дней ([лимиты](https://developers.cloudflare.com/d1/platform/limits/)). Полное внешнее восстановление проверено один раз; регулярного независимого от этого компьютера внешнего резервирования пока нет. Разовая отметка здоровья устаревает через 48 часов — не обновлять её без нового успешного резервирования.

## Фото квартир в R2, 13 ноября 2026

Публикация сама создаёт хранилище R2 `ai-arenda-media` (`scripts/ensure-r2-bucket.mjs`) и подключает его к Worker как `BUCKET`. Новые фото квартир пишутся туда, в D1 остаётся только ссылка (`media.object_key`, миграция 0036). Фото, которые уже лежат в базе, фоновая задача `media-move` переносит по 20 штук в минуту; `media-sweep` раз в час удаляет из R2 фото, чьих строк больше нет (удалённые снимки, удалённые аккаунты). Аватары остаются в D1. С тем же хранилищем включаются фото и видео отчётов уборки в R2 и ежедневная зашифрованная копия базы.

Если R2 на аккаунте не включён или у токена нет права Workers R2 Storage: Edit, публикация не падает: Worker публикуется без хранилища, фото остаются в базе, в журнале публикации появляется пояснение. R2 включается один раз в панели Cloudflare (раздел R2 Object Storage, бесплатный план: 10 ГБ). Если API Cloudflare недоступен во время проверки, публикация останавливается, чтобы уже перенесённые фото не стали недоступны.
