# Подготовка круглосуточной эксплуатации

Это локальная подготовка к размещению. Ни одна команда ниже не создаёт хостинг, не меняет аудиторию существующего сайта, не публикует код и не подключает провайдеров.

## Проверка конфигурации

```powershell
node scripts/check-release.mjs
node scripts/check-release.mjs --production
```

Скрипт читает `.dev.vars` и переменные процесса, выводит только логические результаты, названия недостающих настроек и статусы подключений. Значения ключей, адреса пользователей и секретные URL не выводятся. Для текущего локального режима отсутствие назначенного администратора платформы отмечается как незавершённая подготовка; его ID задаётся вручную серверной настройкой `PLATFORM_ADMIN_IDS`, а не ролью в пользовательской анкете.

Производственная проверка дополнительно требует HTTPS-адрес, собранные Worker/клиент, реальное расписание в итоговой конфигурации Worker и `BACKUP_RECOVERY_VERIFIED=yes`. Последнее — подтверждение оператора **после** реального испытания восстановления, а не автоматическая гарантия кода. Не устанавливать его лишь для получения зелёного результата.

## Порядок размещения, когда будут аккаунты

1. Выбрать размещение и сохранить текущую аудиторию/права сайта. Настроить отдельные тестовую и рабочую базы. Применить миграции последовательно, сначала на копии данных.
2. Секреты внести в защищённые серверные настройки назначения. Локальный `.dev.vars` не отправлять в Git, клиентские файлы или архивы публичных ресурсов.
3. Настроить расписание вызова уже существующего `scheduled` обработчика. Для текущей очереди нужен частый проход (например, каждую минуту). Само наличие обработчика не включает расписание.
4. Настроить полную резервную копию базы вне сервера, отдельные копии объектов/фото и безопасное отдельное хранение ключа шифрования. Пилотный ограниченный JSON-снимок не заменяет полную копию всех данных.
5. Восстановить тестовую базу и фото на отдельном окружении, проверить доступ и целостность, зафиксировать время восстановления. Только после этого подтвердить `BACKUP_RECOVERY_VERIFIED=yes`.
6. Запустить внешний мониторинг `/api/internal/health`. Секрет передавать только в Bearer-заголовке. Падение самого сервера должен замечать процесс, работающий независимо от него. Доставку оповещений настроить с выбранным провайдером отдельно.
7. Проверить полный пользовательский цикл трёх ролей и реальную очередь/календари. Затем подключать мессенджеры и банковские адаптеры с фактическими аккаунтами.

## Healthcheck

```powershell
node scripts/healthcheck.mjs --url http://127.0.0.1:5173
```

Для внешнего сервера допускается только HTTPS. Можно задать `HEALTHCHECK_BASE_URL` в среде запуска. `ADMINISTRATOR_RUNNER_SECRET` берётся из среды/локального файла и не помещается в URL/аргументы/вывод. Скрипт ничего не отправляет в мессенджеры и не создаёт автоматизаций Codex; он завершается ненулевым кодом при проблеме, чтобы его мог использовать независимый монитор.

Закрытый ответ содержит только возраст успешной фоновой проверки и копии, счётчики зависших/просроченных/исчерпавших попытки заданий, ошибки обновления календарей/доставки и логические признаки конфигурации. Адреса, имена, идентификаторы объектов, токены источников и тексты ошибок не возвращаются. Порог свежести координатора — 180 секунд, копии — 48 часов. Пустая новая база без прохода и копии честно показывает `needs_attention`.

Наличие настроек и зелёный healthcheck показывают состояние механизма в данный момент, но не доказывают круглосуточную доступность, корректность банковского API или восстановимость всех объектов. Эти свойства проверяются при размещении и последующей эксплуатации.
